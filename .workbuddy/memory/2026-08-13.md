## Webhook 407 排查结论

- 现象：`http://127.0.0.1:3000/api/webhook/paddle-transaction-completed` 返回 `407 Request blocked/denied`。
- 结论：应用代码本身没问题（全库无 407；`proxy.ts` 只拦 `/dashboard`；本地与生产端点均正确返回 `401 invalid_signature`）。407 来自 Paddle 侧/网络层：通知目标 URL 配成了回环地址 `127.0.0.1`，Paddle 出网代理会拦截 loopback/内网地址（SSRF 防护）。
- 修复：Paddle 通知目标应改为公网地址 `https://licentra.henri.ren/api/webhook/paddle-transaction-completed`（已部署在 Vercel，可正常返回 401）。本地联调用 ngrok/cloudflared/Hookdeck 隧道。
- 其他：`PADDLE_WEBHOOK_SECRET` 每个通知目标独立、沙盒/生产不同；`.env.local` 里 `NEXT_PUBLIC_APP_URL=https://licentra.henri.ren`。
- 环境备注：WorkBuddy 沙盒 shell 里有 `HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:57252`（无 NO_PROXY），本地测试工具若遵循该变量可能干扰 localhost 请求。

## 后续：生产 401 invalid_signature 定位

- 用本地 `.env.local` 的 secret 构造签名请求，同时 POST 生产(Vercel)与本地，**均返回 400 wrong_event_type**（签名通过），证明：应用侧 secret 在本地与 Vercel 一致、`request.text()` 原始 body 无误、验证逻辑正确。
- 结论：用户看到的 401 `invalid_signature` 是 **Paddle 通知目标的 secret 与应用 `PADDLE_WEBHOOK_SECRET` 不匹配**（大概率沙盒/生产密钥搞混，或抄错目标）。`PADDLE_ENVIRONMENT` 在代码里未被使用，不影响校验。
- 修复方向：Paddle 后台对应通知目标（notification destination）的 Secret Key 覆盖 `PADDLE_WEBHOOK_SECRET`（本地 .env.local + Vercel 环境变量同步）；沙盒与生产是两套独立密钥。

## 最终根因（已修复）

- **真正的 bug 在 `src/lib/paddle.ts` 的 `verifyPaddleSignature`**：HMAC 签名字符串分隔符写成了点号 `.`，而 Paddle 官方算法是冒号 `:`（`HMAC-SHA256(key, `${ts}:${rawBody}`)`）。这导致无论 secret 怎么改都必然 401。
- 已修复：`${parsed.ts}.${rawBody}` → `${parsed.ts}:${rawBody}`（含注释）。已验证：冒号通过(400 wrong_event_type)、点号拒绝(401)。
- 顺手清理了 `PADDLE_ENVIRONMENT`（env.ts / .env.example / .env.local / docs/PROJECT.md），代码中无其它引用。
- 遗留待办：`.env.local` 的 `PADDLE_WEBHOOK_SECRET` 仍是占位符 `"xxxxxxx"`，需替换为 Paddle 后台真实 secret（`pdl_ntfset_` 前缀），Vercel 同步并重新部署（代码+env 改动都需要 redeploy 才生效）。

## 幂等逻辑 bug（已修复）

- 现象：同一事件第一次报 500（amount 错），第二次返回 `{"ok":true,"duplicate":true}`，但订单**没建出来**。
- 根因：`processWebhookEvent` 里 `if (existing)` 只要 WebhookEvent 行存在就返回 duplicate，**不看 `processed` 字段**。第一次失败留下了 `processed=false` 的行，导致所有重试被误判为重复而跳过，且返回 200 让 Paddle 停止重试 → 事件卡死。
- 已修复：改为 `row?.processed` 才返回 duplicate；`processed=false` 时复用已有行重跑 handler（handler 本身在 Order 层幂等，`paddleTransactionId` unique）。已验证：processed=false → 重跑 200 ok 且 processed 置 true；processed=true → 200 duplicate。
- 补救：真实交易 `txn_01kzwrhjfsk0wgs1wkyypjtcc7`（event `evt_01kzwrkch3rw445g6d2y2zsqrd`）已卡住，部署后需在 Paddle 通知日志里 Replay 该事件重放。
