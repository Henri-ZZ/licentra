## ErrorEvent 排查（RSC 流式渲染失败）

- 现象：浏览器 `ErrorEvent`，dev 日志 `⨯ Error: [object ErrorEvent]`，栈在 react-server-dom-turbopack-client 的 resolveErrorDev。
- 根因：**.next 里混入了生产构建产物**（`.next/build-manifest.json`、`.next/server`，是上一轮为验证改动跑的 `next build` 留下的），随后启动的 `pnpm dev` 对着这份混合缓存跑 RSC 流式渲染 → 服务端流错误被序列化成通用 ErrorEvent，真实信息被吞。
- 处理：`mv .next .next.mixed-<ts>`（混合缓存移出），需用户 Ctrl+C 停掉还在跑的 dev（PID 21288）后重新 `pnpm dev`，浏览器硬刷新。
- 待清理目录：`.next.corrupt-1786713545`（昨日 CSS 损坏缓存）、`.next.mixed-1786750368`（本次），确认 dev 正常后可删。

### 教训
- **不要在 dev server 运行期间/之后跑 `next build` 污染 `.next`**。验证构建后必须清掉 `.next` 再让用户起 dev（`mv .next .next.bak-*` 只是绕 safe-delete 的临时手段，别忘了清理 + 复原）。
- ErrorEvent / "[object ErrorEvent]" 在 dev 里出现时，优先怀疑 `.next` 状态而非业务代码；先看 `.next/dev/logs/next-development.log` 和 `.next` 是否混有生产产物。

## id 精简：cuid(25) → nanoid(10)（用户要求）

- **Prisma 7.9.1 原生支持 `@default(nanoid(10))`**（`cuid(10)` 不支持，只接受 `cuid(1)`/`cuid(2)` 版本参数；validate 实测确认）。零依赖、零扩展代码。
- 8 个模型全部替换：Product / ProductPriceTier / ProductEmailTemplate / License / Activation / SigningKey / AuditEvent / Order。
- nanoid 是**客户端侧默认值**：`db push` 无 diff（"already in sync"），存量 25 位 id 保留，新行 10 位 → 新老混用（无害，License.id 即 license_id，客户端按不透明字符串处理）。
- 碰撞安全：nanoid 默认 64 字符表 × 10 位 ≈ 2^60，百万级无风险。
- 文档：price-tiers.md schema 片段、EXTERNAL/FRONTEND.md 的 "cuid" 措辞已改（cuid→id / nanoid(10)）。
- 验证：validate ✅ generate ✅ tsc ✅ db in sync ✅。**未跑 next build**（避免再次污染 dev 的 .next）。
